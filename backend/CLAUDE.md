# Backend Map — Go API

Module: `github.com/Ulisesgtz/medic-track/backend`. Router: `chi`. DB: PostgreSQL via `pgxpool`.

## Known cross-cutting rules to keep in sync when touching name/account fields

- Name format rule (letters incl. accents/ñ, spaces, hyphens, apostrophes, max 100 chars) is owned by the **application layer only** — `internal/account/service.go`'s `namePattern` (Go `\p{L}`) and `frontend/src/features/account-signup/types.ts`'s `NAME_PATTERN` (JS `\p{L}`), which agree since both use the full Unicode "letter" category. The DB CHECK constraint (`migrations/0004_add_name_constraints.sql`) deliberately enforces **length only** — an earlier version also checked character set with an explicit Latin-1 range, which silently diverged from `\p{L}` and rejected valid non-Latin names as an opaque 500; don't reintroduce a character-class regex there.
- Child limit by plan (spec 029): `service.go`'s `ChildLimit(plan)` — `free` = `freePlanChildLimit` (1, also what `CreateAccount` checks: a new account is always free), `paid` = `paidPlanChildLimit` (10; a ceiling, not "unlimited"), anything else = free. `AddChildIfUnderLimit` reads the plan under its row lock and applies `ChildLimit` itself (no `limit` parameter). The frontend has its own `FREE_PLAN_CHILD_LIMIT` in `features/home/plan.ts` and only looks at `account.plan === 'free'` — update both if the free limit changes. **There is no endpoint to change a plan** (payments are future work): to give someone the paid plan, in the database `UPDATE accounts SET plan = 'paid' WHERE lower(email) = lower('…');` (`'free'` takes it back; children already created stay). A paid account that reaches 10 gets the same 422 `freemium_child_limit_exceeded` (its `limit` says 10), which the app still words as the free plan's pop-up.
- `CreateAccount` checks the freemium limit **before** field-level validation, so a request with 2+ children always gets `422 freemium_child_limit_exceeded` rather than a `400` about some unrelated field on the extra child.

## Sharing with the family (specs/032-compartir-con-familia)

- **Routes** (all in `internal/server/router.go`, all behind `RequireSession`): `GET /family`, `POST /family/invitations`, `POST /family/invitations/{id}/resend|cancel`, `POST /family/invitations/preview|accept|decline` (token in the body), `POST /family/members/{id}/remove`, `POST /family/leave`. They name no child/consultation, so there is no `RequireAccess` in front: the service reads the session's family and level itself. Every route that **does** name a child, consultation or owner account is guarded by a level: `seesChild`/`seesConsultation` (`Mark`: read and mark), `fullChild`/`fullConsultation`/`fullAccount` (`Full`: create consultations, end/extend treatments, add children — `POST /accounts/{accountId}/children` takes the **owner's** account id, so a Tutor adds to the family and the plan and the child limit are the owner's). `router_test.go` walks every route for the owner, a Tutor, a Caregiver, a Child-role member, a removed person, a Tutor of a lapsed family and a stranger — **a new route needs its level and a row there**.
- **`GET /accounts/me`** now also lists the children shared with the person (a Tutor/Caregiver: every child of the family; a Child-role member: only theirs), after their own, each with `accountId` (the owner), `role` (`owner` for their own), `plan` (**the family's**) and `readOnly`; and a `family` section (`role`, `ownerAccountId`, `ownerName`, `plan`, `readOnly`) when the person is a member. Own children keep working exactly as before.
- **Doses with an author.** `doses.taken_by_account_id` + `taken_at` (CHECK: both null unless `taken`). `UpdateDoseStatus(…, actor)`: the **first mark wins** (`UPDATE … AND NOT taken`, then the dose as it was); unmarking is allowed to the author or to a `Full` actor, otherwise `ErrDoseForbidden` → 403; a mark from before the feature (no author) is only taken back by a `Full`. Dose JSON has `takenBy {name, at, mine}` (`name` = first name, **never the e-mail**; `mine` = the session's account marked it).
- **Reminders per person** (`reminder.ClaimDueDoses`): one statement claims **(dose, person) pairs** — each account with at least `Mark` access to the child (owner, active Tutor/Caregiver, the Child-role member of that child) that has an active device activated before the dose — with `INSERT INTO dose_reminders … ON CONFLICT DO NOTHING RETURNING` (the primary key is what makes one reminder per dose and person at most, across restarts and instances) and keeps stamping `doses.reminder_sent_at` for compatibility. A taken dose is never a candidate, so nobody is reminded of what another person already marked; a person who left or was removed is no longer a recipient from the next tick on, with their devices untouched. `DueDose.AccountID`/`Detail` are the **recipient's**; `Tick` sends to that person's devices with their own detail/generic choice. «Tomada» marks as the account of the **device** that received it and only while that account still has access (`MarkTakenByAction`).
- **A lapsed family is read-only, not blocked:** the owner not being `paid` caps invited people at `Mark` (they see everything, mark and unmark their own, add nothing); inviting and accepting answer 422 `freemium_consultation_limit_exceeded` with `reason: "family"`. Nothing is hidden or deleted; the role comes back by itself when the owner is `paid` again.
- **Free** accounts can't invite (422 `family`), but can be a member of a paid family. The disclaimer version was bumped (`2026-10-06`) with the new text: sharing means another person sees the minor's medical data.

## Automatic error logging (specs/002-registro-log-errores)

**History search (spec 031).** `internal/consultation/search.go`: `Repository.Search` (`POST /children/{childId}/consultations/search`) and `HistoryOptions` (`GET /children/{childId}/history-options`), both behind `ownsChild` and the **paid plan**: `requirePaid` reads `accounts.plan` first and a free account gets `*PlanLimitError{Reason: PlanLimitHistorySearch}` → **422** `freemium_consultation_limit_exceeded` / `reason: "history_search"` with no rows, whatever it asked (even `{}`); the plain list (`GET …/consultations`) is untouched and is what a free account sees. **The criteria are a POST body, never a query string** — `middleware.Logger` prints the full address (and Railway/Cloudflare keep theirs), and what a parent types can be health information; `error_logs` keeps only the route template. `HistorySearch` (`q`, `from`, `to`, `doctor`, `medication`, `symptomCodes`, `kind`): `validateHistorySearch` runs first in `Service.SearchConsultations` (trims; `q` ≤ 100 runes, `doctor`/`medication` ≤ 200, `kind` ∈ `all|treatment|record`, `from ≤ to`, ≤ 30 deduplicated codes; field errors named as in the contract) and an invalid criterion never reaches the database; a code the catalog never had (retired ones count) is `ErrSymptomNotAvailable` → 400 `symptom_not_available`. The SQL is built from fixed fragments with positional arguments (never pasted text): `q` is `strpos(fold(col), fold(q)) > 0` over the doctor, the notes or an `EXISTS` medication name — **`foldSpanish`/`sqlFold` (`translate(lower(x), 'áéíóúüñÁÉÍÓÚÜÑ', 'aeiouunaeiouun')`, the upper-case ones listed because `lower()` depends on the database locale) are twins and `TestSearch_SQLAndGoFoldTheSameWay` keeps them equal**; no `unaccent` extension, no migration, `strpos` has no wildcards to escape; dates are `consult_date` bounds, both ends included; symptoms: `count(DISTINCT symptom_code) = n` (the consultation must have **all** of them); `kind` is `record_only`. Same row shape and scan (`scanSummaries`) as the list; order `consult_date DESC, created_at DESC, id`; nothing paged. `HistoryOptions` returns distinct trimmed doctor and medication names as written (not unified), sorted by their folded text, `[]` not `null`. Both are registered in `server/router.go` with a row each in `router_test.go`.

**Free plan rules for consultations (spec 030).** `consultation.Repository.Create` calls `checkPlan` right after the child is known to exist, in the same transaction: it locks the account row (`SELECT … FOR UPDATE OF a`, joined from the child, so two requests of one account are checked one after the other) and, if `accounts.plan` is not `paid` (the column is read directly, `consultation` doesn't import `account`), refuses with a `*PlanLimitError` (`errors.Is(err, ErrPlanLimit)`): `Reason` `record_only` when `RecordOnly` is true (even with nothing running), else `active_treatment` when **any child of the account** has a medication with `ended_at IS NULL` and a dose with `scheduled_at > now` (the same "active" as `GetOverview`; `now` is `r.now()`). Nothing is saved and nothing already saved changes or is hidden — only creating is refused; reads and marking doses are never affected. The handler maps it to **422** `{error: "freemium_consultation_limit_exceeded", message, reason}` (`planLimitBody`, documented as `PlanLimitResponse`; same code family as the child limit's `freemium_child_limit_exceeded`). **Tests that aren't about the plan use a paid account**: `createTestChild` (consultation) and the account insert of `reminder/testhelpers_test.go` are `paid`; `createFreeTestChild`/`createChildren` build the free ones (`plan_test.go` covers the rules, the race and the 422). A plan is still given by hand with SQL (see "Child limit by plan" above).

**Record-only consultations (spec 024).** `consultations.record_only` (migration `0016`, `BOOLEAN NOT NULL DEFAULT false`) is written once by `Repository.Create` and never updated (consultations are immutable). `CreateConsultationInput.RecordOnly` (JSON `recordOnly`, optional): the service neither requires nor validates the medications' `startTime` and **discards it** (`StartTime = nil`) — the server, not the client, guarantees "no schedule"; name, frequency and duration are validated as usual, and a future `consultDate` is still rejected. Because `generateDoseSchedule` returns nothing without a start time, **no doses exist**, so everything derived from doses (`GetOverview`, active treatment, `StatusAt`, `ClaimDueDoses`, end/extend) needs no special case — tests in `recordonly_test.go` (both `consultation` and `reminder`) pin that. `recordOnly` is in the list and detail responses (always present).

**Extending a treatment (spec 020).** Only because the parent decided (never automatic or suggested; Principio I). `medication_extensions` (migration `0014`, append-only: `medication_id`, `account_id` = the account that owns the consultation, `proposed_doses`, `added_doses` 1–60; `added ≠ proposed` = "ingresado manualmente") and two nullable columns on `doses`: `added_by_extension_id` and `covered_by_extension_id`. `Medication.ExtendableDoses` (read by `GetByID`, `uncoveredUnregistered`) = doses in `unregistered` status (spec 013 rule, server clock) not yet covered, 0 once ended. `Repository.ExtendTreatment` runs in one transaction with the medication `FOR UPDATE`: `ErrNothingToExtend` if ended or nothing uncovered (also what a second tap or device gets — nothing is ever covered twice), records the extension, marks **all** the unregistered doses covered whatever number was confirmed, and appends N doses at `max(scheduled_at) + k × frequency`. Route `POST /consultations/{consultationId}/medications/{medicationId}/extend` body `{ "doses": N }` (`ownsConsultation`; 400 `validation_error` field `doses` / `nothing_to_extend`, 404 `medication_not_found`); `MaxExtensionDoses = 60`. The added doses are ordinary doses (reminders, progress, overview). The second exception to consultations being immutable (spec 004 FR-014): doses are added, nothing is edited or deleted. `consultation.SetNow` (export_test.go) fixes the repository clock in tests.

**Ending a treatment (spec 016).** `medications.ended_at` (migration `0013`, NULL = running) is the only thing that changes; no dose is touched. `StatusAt(…, endedAt, now)` adds `canceled`: not marked and `scheduledAt > endedAt` (checked before pending/due/unregistered; doses already come keep their status and stay markable). `Repository.EndTreatment` is idempotent (keeps the first moment), `ErrMedicationNotFound` (also for a medication of another consultation) and `ErrNothingToEnd` (400 `nothing_to_end`); route `POST /consultations/{consultationId}/medications/{medicationId}/end` with `ownsConsultation`. `GetOverview` leaves out canceled doses and ended medications (active treatment); `ClaimDueDoses` never claims a canceled dose. The first exception to consultations being immutable (spec 004 FR-014); spec 020 adds the second.

**Dose status (spec 013).** `consultation.StatusAt(scheduledAt, taken, frequencyHours, now)` is the one rule: taken; else pending before its time; else `unregistered` from `scheduledAt + frequencyHours` (when the medication's next dose comes, also for the last one); else `due`. It is derived, never stored, with the server's clock (`Repository.now`), and sent as `status` in every dose (detail, create, `PATCH`, overview). `reminder.ClaimDueDoses` never claims a dose already unregistered.

**Symptoms (spec 012).** `symptoms` is maintained with SQL, never by publishing the app: add = `INSERT` with a free `sort_order` (`ListSymptoms` keeps each category together, categories ordered by their first symptom, so a later `sort_order` in an existing category still joins it), retire = `UPDATE symptoms SET active = false` (no longer offered, still shown on the consultations that have it), rename = `UPDATE … SET name`. Never delete a row or change a `code`. `consultation_symptoms` carries the consultation's `child_id` and that child's `account_id` so symptoms can be read per child or per account; composite foreign keys to `consultations (id, child_id)` and `children (id, account_id)` make the database reject any other pair. `consultation.Repository.Create` inserts them in the consultation's transaction with an `INSERT … SELECT` that takes the account from `children` and accepts only active symptoms; fewer rows than codes → `ErrSymptomNotAvailable` → 400 `details[{field: "symptomCodes", message: "symptom_not_available"}]`, nothing saved (the repository removes repeated codes itself before counting). The create request still accepts the pre-012 `"symptoms": "<text>"` as the notes (`notesOf` in `handler.go`) so an older frontend bundle doesn't lose the text while both versions are deployed. The symptom type and JSON shape are the catalog's (`catalog.Symptom`, `catalog.SymptomResponse`), shared by the consultation detail. Tests that need extra symptoms add `test_…` rows far after the seed and remove them (`tempSymptom` in `symptoms_test.go`).

**Every new handler package (any new feature/endpoint) MUST take a `*httpx.Responder` in its constructor and write ALL its JSON responses through it** — same pattern as `account.NewHandler`/`catalog.NewHandler`. This is not optional or feature-specific: it's how every backend response in this codebase gets written, and it's what makes error logging automatic for free. There is no other supported way to write a JSON response here (the old package-level `httpx.WriteJSON`/`WriteJSONError` functions were deleted specifically so this can't be bypassed).

Every handler constructor now takes a `*httpx.Responder` (built once in `cmd/api/main.go` via `httpx.NewResponder(errorlog.NewRepository(pool))`) instead of calling package-level `httpx` functions. Any response written through `Responder.WriteJSON`/`WriteJSONError` with a 4xx/5xx status is automatically logged to `error_logs` — no handler code has to opt in per call site. Key points if you touch this:

- **Never call the old `httpx.WriteJSON`/`httpx.WriteJSONError` package functions** — they don't exist anymore; use `h.responder.WriteJSON(ctx, w, status, body, accountID)` (pass `accountID` as `nil` when no account is known yet, e.g. before signup succeeds).
- File/line are captured automatically via `runtime.Caller` inside `Responder.record` — don't add a `file`/`line` parameter to handler call sites, and don't add another layer of indirection between a handler and `Responder` without checking the `skip` offset in `internal/httpx/json.go` still resolves correctly.
- The actual DB write happens in a detached background goroutine with its own timeout — a slow/down `error_logs` insert must never delay or break the HTTP response already sent (verified by `TestResponder_WriteJSONError_RecorderFailureDoesNotAffectResponse` and the latency test in `internal/httpx/json_test.go`).
- The log NEVER stores the user's email — only `account_id` (nullable UUID). Don't add an email field to `errorlog.Entry`.
- Reading it and purging it by age is spec 021 (`internal/ops`, `internal/retention`); no edit or export, and the weekly e-mail digest is still future work — see `BACKLOG.md`.
- Background processes (no request) report through `internal/jobreport`, not `httpx` (specs/018).

## API docs (Swagger)

Every handler (`account`, `catalog`, `consultation`, `reminder` — every route registered in `internal/server/router.go` has its `@Router`) carries `@Summary`/`@Param`/`@Success`/`@Failure`/`@Router` doc comments (swaggo/swag syntax) directly above the function. The Swagger UI is served at `http://localhost:8080/swagger/index.html` when the API is running (`go run ./cmd/api`) — use it to explore endpoints, payload/response shapes, and to try requests live against your local DB.

**After changing any handler's request/response types or doc comments**, regenerate the docs:

```bash
go run github.com/swaggo/swag/cmd/swag init -g cmd/api/main.go -o internal/docs --pd
```

CI fails the build if `internal/docs/` is stale relative to the annotations (it re-runs the same command and diffs the output), so always commit the regenerated files together with the handler change.
