# Backend Map — Go API

Module: `github.com/Ulisesgtz/medic-track/backend`. Router: `chi`. DB: PostgreSQL via `pgxpool`.

## Layout

| Path | What's there |
|---|---|
| `cmd/api/main.go` | Entry point: wires DB pool, repos/services/handlers, chi router, CORS, routes |
| `internal/account/` | Account + Child domain: signup, freemium limit, name validation, reading an account and adding a child to an existing one (specs/003-home-listado-hijos) |
| `internal/account/model.go` | `Account`, `Child` structs |
| `internal/account/errors.go` | Domain errors (`ErrEmailAlreadyExists`, `ErrFreemiumChildLimitExceeded`, `ErrInvalidNameFormat`, `ErrAccountNotFound`), `ValidationErrors`, `FreemiumLimitError` (wraps `ErrFreemiumChildLimitExceeded` with the actual `Limit`/`Received` counts via `Unwrap`) |
| `internal/account/service.go` | `CreateAccount` — freemium limit check against the shared `freePlanChildLimit` constant (runs first), then field validation (required fields, email format, name format/length via `validateNameFormat`, birth date, height/weight). `validateChildFields` factors out the single-child validation rules (unprefixed field names) that both `validateCreateAccountInput` and `AddChild` build on. `GetAccount` backs the home page's `GET` endpoint. `AddChild` validates fields, then delegates the freemium-limit check + insert to `repo.AddChildIfUnderLimit` as one atomic operation (see repository.go) — it does NOT check-then-insert itself, to avoid a TOCTOU race. |
| `internal/account/repository.go` | SQL: inserts Account + Children in one transaction; `mapInsertError` maps pg 23505→`ErrEmailAlreadyExists`, pg 23514 (CHECK violation)→`ErrInvalidNameFormat`. `GetByID` (→`ErrAccountNotFound` if missing) backs `GetAccount`. `AddChildIfUnderLimit` backs `AddChild`: locks the account row (`FOR UPDATE`), counts children, and inserts — all in one transaction, so two concurrent "add a child" requests for the same account can't both pass the limit check (see `TestRepository_AddChildIfUnderLimit_LimitExceeded`). |
| `internal/account/` (spec 008) | `POST /accounts` answers in this order: session (401) → body (400) → the session already has an account (200, no Clerk call) → the session's **verified** primary email from Clerk (403 if unverified, 500 if Clerk is down) → a legacy account (`clerk_user_id IS NULL`) with that email, case-insensitive, is **linked** (`Repository.LinkByEmail`, 200) → create (201). `GET /accounts/me` links the same way on first access. Two twin `POST /accounts` for one session: the loser gets the winner's account (`ErrClerkUserAlreadyLinked` → idempotent 200). |
| `internal/account/disclaimer.go` (spec 010) | `CurrentDisclaimerVersion` (a date; **bump it whenever the wording of the frontend's "Antes de empezar" banner changes** — every account is then asked again) and the `DisclaimerAcceptance` record. `Repository.AcceptDisclaimer` inserts `(account, version)` into `disclaimer_acceptances` with `ON CONFLICT DO NOTHING` and returns the original `accepted_at`; `disclaimerAccepted()` (used by `GetByID`, `GetByClerkUserID` and `AddChildIfUnderLimit`) fills `Account.DisclaimerAccepted`, so every account response says whether the current version was acknowledged. `Service.AcceptDisclaimer` rejects any other version. |
| `internal/account/handler.go` | `POST /accounts`, `GET /accounts/{accountId}`, `POST /accounts/{accountId}/children`, `POST /accounts/{accountId}/disclaimer-acceptance`, `PATCH /accounts/{accountId}/reminder-settings` (spec 011: `reminderDetail` "detailed"/"generic", null until chosen, on every account response) — request/response shapes, maps domain errors → HTTP status. An `accountId` that isn't a well-formed UUID is treated as 404, same as a genuinely missing account. |
| `internal/reminder/` (spec 011) | Dose reminders by Web Push. `Repository`: `UpsertDevice` (idempotent by `endpoint`; an endpoint of another account **moves** to this one — a browser reminds one account), `DeactivateDevice`/`DeactivateByID`, `ClaimDueDoses` (one `UPDATE … FOR UPDATE SKIP LOCKED … RETURNING` sets `doses.reminder_sent_at`: not taken, due in the last 60 min, account with an active device activated before the dose — **claiming before sending is what guarantees at most one reminder per dose**), `ActiveDevicesFor`, `MarkTakenByAction`. `Service.Tick` claims → builds the payload (generic unless the account chose "detailed"; generic carries no medication/child at all) → sends with 8 at a time → 404/410 turns the device off, other failures are not retried. `ActivateDevice` only accepts **https endpoints of the known push services** (`pushServiceHosts`: FCM, Mozilla, Apple, Windows) — the server POSTs to that URL, so anything else would be an SSRF. `actiontoken.go`: HMAC-SHA256 token (dose, device, 24 h) for the public "Tomada" action. `scheduler.go`: `RunScheduler` ticks every 30 s in the API process (started from `cmd/api` only when `Config.Available()`). Never log a device endpoint, its keys or a token: `Tick` deliberately drops the sender's error text |
| `internal/catalog/` | Read-only reference data, all public: country/state catalog (`GET /catalog/countries`, `GET /catalog/countries/{code}/states`) and the **symptoms catalog** (`GET /catalog/symptoms`, spec 012: active symptoms in `sort_order`, each with its category title) |
| `internal/consultation/` | Consultation + Medication + Dose domain (specs/004-detalle-consulta-hijo): registering a medical visit and marking doses as taken. Everything is immutable except `Dose.taken` — no edit/delete endpoint exists for Consultation/Medication. `AddChildIfUnderLimit`-style atomicity isn't needed here (no shared limit to race on); `Create` still runs as one transaction so a consultation, its medications, and all generated doses either all persist or none do |
| `internal/consultation/` (spec 006) | `GET /children/{childId}/overview?from=&to=` — `Repository.GetOverview` returns the doses scheduled in `[from, to)` (the parent's local "today", sent by the client) and the *active treatment* (medication whose last dose is furthest in the future; derived only from the schedule, never a medical judgement). `Service.GetChildOverview` rejects windows that aren't positive or exceed 48h. The consultations list also returns `symptoms` and `medicationCount`. `POST .../consultations` takes an optional `utcOffsetMinutes`: `Consultation.ScheduleLocation` makes `generateDoseSchedule` read each medication's `StartTime` in the parent's zone so dose instants are real (0/omitted = UTC, the old behaviour). |
| `internal/authmw/` | `RequireSession` (verifies the Clerk token → 401 through the `Responder`) and `RequireOwner(responder, param, check)` (403 unless the session owns the resource in the route param — runs before the handler; a nonexistent resource is 403 too, a malformed id falls through to the handler's own 404). `authmwtest` mints real signed sessions for tests without touching the network |
| `internal/ownership/` | The three ownership queries (`OwnsAccount`/`OwnsChild`/`OwnsConsultation`), each one `EXISTS` over `accounts.clerk_user_id` and `children.account_id` — the only source of truth for who owns what; consultations have no `account_id` of their own |
| `internal/server/` | `NewRouter(Deps)`: **the only place routes are registered.** Only `/catalog/*` and `POST /reminders/actions/taken` (a reminder's "Tomada" button, spec 011 — it accepts nothing but a valid signed action token) are public; everything else is behind `RequireSession`, and every route with an `{accountId}`/`{childId}`/`{consultationId}` also has `RequireOwner`. `router_test.go` walks every protected route (401 / 403 / owner reaches the handler) — **a new endpoint that names one of those ids must get its `RequireOwner` here and a row in `routes()` in that test** |
| `internal/platform/db.go` | `NewPostgresPool` — reads `DATABASE_URL` |
| `internal/httpx/` | `Responder` (constructed via `NewResponder(recorder)`) — `WriteJSON`/`WriteJSONError` methods used by both `account` and `catalog` handlers; every 4xx/5xx response it writes is automatically logged to `error_logs` in a background goroutine, see "Automatic error logging" below. Also `FieldError` + `ValidationBody(message, errs)`: the one shape of a `validation_error` body (`{error, message, details: [{field, message}]}`) — every package that returns field errors builds it with this instead of its own copy |
| `internal/errorlog/` | `Entry` model + `Repository.Create` — persists rows in `error_logs` (specs/002-registro-log-errores); no read/query in this scope on purpose |
| `internal/docs/` | **Generated** OpenAPI/Swagger docs (`docs.go`, `swagger.json`, `swagger.yaml`) — do not hand-edit, see "API docs (Swagger)" below |
| `migrations/*.sql` | Schema, applied manually (no migration tool wired in yet) — `0001` catalog tables + México seed, `0002` accounts, `0003` children, `0004` name length CHECK constraints, `0005` `error_logs` table, `0006`-`0008` `consultations`/`medications`/`doses`, `0009` `accounts.clerk_user_id`, `0010` `disclaimer_acceptances`, `0011` `reminder_devices` + `accounts.reminder_detail` + `doses.reminder_sent_at`, `0012` `symptoms` (catalog + seed) + `consultation_symptoms` + `consultations.symptoms` renamed to `notes` |
| `.github/workflows/ci.yml` | CI: backend coverage gate (incl. verifying Swagger docs are up to date), frontend coverage gate, Playwright E2E gate — all merge-blocking per constitution Principio VI |

## Known cross-cutting rules to keep in sync when touching name/account fields

- Name format rule (letters incl. accents/ñ, spaces, hyphens, apostrophes, max 100 chars) is owned by the **application layer only** — `internal/account/service.go`'s `namePattern` (Go `\p{L}`) and `frontend/src/features/account-signup/types.ts`'s `NAME_PATTERN` (JS `\p{L}`), which agree since both use the full Unicode "letter" category. The DB CHECK constraint (`migrations/0004_add_name_constraints.sql`) deliberately enforces **length only** — an earlier version also checked character set with an explicit Latin-1 range, which silently diverged from `\p{L}` and rejected valid non-Latin names as an opaque 500; don't reintroduce a character-class regex there.
- Freemium child limit (`1`) is `service.go`'s `freePlanChildLimit` constant on the backend (used by both `CreateAccount` and `AddChild`) and a separate constant in `frontend/.../AccountSignupForm.tsx` (`FREE_PLAN_CHILD_LIMIT`) — update both if the limit or plan model changes.
- `CreateAccount` checks the freemium limit **before** field-level validation, so a request with 2+ children always gets `422 freemium_child_limit_exceeded` rather than a `400` about some unrelated field on the extra child.

## Automatic error logging (specs/002-registro-log-errores)

**Symptoms (spec 012).** `symptoms` is maintained with SQL, never by publishing the app: add = `INSERT` with a free `sort_order` (`ListSymptoms` keeps each category together, categories ordered by their first symptom, so a later `sort_order` in an existing category still joins it), retire = `UPDATE symptoms SET active = false` (no longer offered, still shown on the consultations that have it), rename = `UPDATE … SET name`. Never delete a row or change a `code`. `consultation_symptoms` carries the consultation's `child_id` and that child's `account_id` so symptoms can be read per child or per account; composite foreign keys to `consultations (id, child_id)` and `children (id, account_id)` make the database reject any other pair. `consultation.Repository.Create` inserts them in the consultation's transaction with an `INSERT … SELECT` that takes the account from `children` and accepts only active symptoms; fewer rows than codes → `ErrSymptomNotAvailable` → 400 `details[{field: "symptomCodes", message: "symptom_not_available"}]`, nothing saved (the repository removes repeated codes itself before counting). The create request still accepts the pre-012 `"symptoms": "<text>"` as the notes (`notesOf` in `handler.go`) so an older frontend bundle doesn't lose the text while both versions are deployed. The symptom type and JSON shape are the catalog's (`catalog.Symptom`, `catalog.SymptomResponse`), shared by the consultation detail. Tests that need extra symptoms add `test_…` rows far after the seed and remove them (`tempSymptom` in `symptoms_test.go`).

**Every new handler package (any new feature/endpoint) MUST take a `*httpx.Responder` in its constructor and write ALL its JSON responses through it** — same pattern as `account.NewHandler`/`catalog.NewHandler`. This is not optional or feature-specific: it's how every backend response in this codebase gets written, and it's what makes error logging automatic for free. There is no other supported way to write a JSON response here (the old package-level `httpx.WriteJSON`/`WriteJSONError` functions were deleted specifically so this can't be bypassed).

Every handler constructor now takes a `*httpx.Responder` (built once in `cmd/api/main.go` via `httpx.NewResponder(errorlog.NewRepository(pool))`) instead of calling package-level `httpx` functions. Any response written through `Responder.WriteJSON`/`WriteJSONError` with a 4xx/5xx status is automatically logged to `error_logs` — no handler code has to opt in per call site. Key points if you touch this:

- **Never call the old `httpx.WriteJSON`/`httpx.WriteJSONError` package functions** — they don't exist anymore; use `h.responder.WriteJSON(ctx, w, status, body, accountID)` (pass `accountID` as `nil` when no account is known yet, e.g. before signup succeeds).
- File/line are captured automatically via `runtime.Caller` inside `Responder.record` — don't add a `file`/`line` parameter to handler call sites, and don't add another layer of indirection between a handler and `Responder` without checking the `skip` offset in `internal/httpx/json.go` still resolves correctly.
- The actual DB write happens in a detached background goroutine with its own timeout — a slow/down `error_logs` insert must never delay or break the HTTP response already sent (verified by `TestResponder_WriteJSONError_RecorderFailureDoesNotAffectResponse` and the latency test in `internal/httpx/json_test.go`).
- The log NEVER stores the user's email — only `account_id` (nullable UUID). Don't add an email field to `errorlog.Entry`.
- No read/query endpoint, and no retention/purge policy exist for `error_logs` on purpose — see `BACKLOG.md`.

## API docs (Swagger)

Every handler (`account`, `catalog`, `consultation`, `reminder` — every route registered in `internal/server/router.go` has its `@Router`) carries `@Summary`/`@Param`/`@Success`/`@Failure`/`@Router` doc comments (swaggo/swag syntax) directly above the function. The Swagger UI is served at `http://localhost:8080/swagger/index.html` when the API is running (`go run ./cmd/api`) — use it to explore endpoints, payload/response shapes, and to try requests live against your local DB.

**After changing any handler's request/response types or doc comments**, regenerate the docs:

```bash
go run github.com/swaggo/swag/cmd/swag init -g cmd/api/main.go -o internal/docs --pd
```

CI fails the build if `internal/docs/` is stale relative to the annotations (it re-runs the same command and diffs the output), so always commit the regenerated files together with the handler change.

## Environment

| Variable | Required | Notes |
|---|---|---|
| `DATABASE_URL` | yes | Postgres |
| `CLERK_SECRET_KEY` | yes | The API refuses to start without it (spec 008) |
| `VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY`, `VAPID_SUBJECT`, `REMINDER_ACTION_SECRET` | for reminders | Spec 011. Without all four the API runs and reminders are "unavailable". `VAPID_SUBJECT` is a contact e-mail (a leading `mailto:` is dropped). Generate the keys once (e.g. `npx web-push generate-vapid-keys`); CI makes throwaway ones with Node's `crypto` |

The reminder scheduler runs inside the API process: **reminders only go out while the API runs**, so production needs an always-on process (not a platform that sleeps when idle).

## Running tests

```bash
export DATABASE_URL="postgres://root:abcd1234@localhost:5432/pediTrack?sslmode=disable"  # local dev creds
go test ./... -cover
```

Coverage target: >90% per package (Principio VI of the constitution). `cmd/api` itself has 0% coverage (wiring-only, currently unaddressed — standing open question, not yet resolved with the user) and is excluded from the CI coverage gate for that reason.
