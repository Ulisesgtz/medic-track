# PediTrack — Project Map

Pediatric health-record app for parents in Mexico. Built with Spec-Kit (Spec-Driven Development). Backend Go + PostgreSQL, frontend React PWA. See `backend/CLAUDE.md` and `frontend/CLAUDE.md` for module-level maps of each side.

## Where things live

| Area | Path |
|---|---|
| Governance / principles / stack / test policy | `.specify/memory/constitution.md` |
| Feature specs (spec.md, plan.md, tasks.md, data-model.md, contracts/) | `specs/<NNN-feature-name>/` |
| Backend service | `backend/` — see `backend/CLAUDE.md` |
| Frontend PWA | `frontend/` — see `frontend/CLAUDE.md` |
| Dev server launch config (used by the Browser preview tool) | `.claude/launch.json` |
| CI (coverage + E2E gates) | `.github/workflows/ci.yml` |
| API docs (Swagger UI, generated from Go doc comments) | `http://localhost:8080/swagger/index.html` when the backend is running — see `backend/CLAUDE.md` |
| Backlog (future work decided but not yet spec'd) | `BACKLOG.md` |
| DEV environment guide (deployed: `https://dev.pedi-track.com` + `https://api-dev.pedi-track.com` — Railway backend + Postgres, Cloudflare Pages frontend, DNS at HostGator, branch `develop`) | `DEPLOY.md`; backend image: `backend/Dockerfile` + `backend/railway.json` |
| Guide for the people who test the DEV environment (install on iPhone/Android, what to try, a message to send) | `PROBAR.md` |

## Current features

- `specs/001-registro-cuenta-usuario/` — account signup (tutor + children), freemium 1-child limit, name format/length validation. Implemented on branch `feature/001-registro-cuenta-usuario`, PR: https://github.com/Ulisesgtz/medic-track/pull/1 (base `develop`), merged to `develop`.
- `specs/002-registro-log-errores/` — automatic error logging hook: every 4xx/5xx response gets logged to `error_logs` (message, HTTP status, endpoint, file/line, optional account_id — never email) via `internal/httpx`'s `Responder`, without any handler opting in per call site. Implemented on branch `feature/002-registro-log-errores`, merged to `develop`.
- `specs/003-home-listado-hijos/` — home page: lists the tutor's children (name + age), "Agregar hijo" modal reusing feature 001's form/freemium limit, and the no-auth `account_id`-in-`localStorage` "session" used to return to the home without a real login. Adds `GET /accounts/{accountId}` and `POST /accounts/{accountId}/children` to `internal/account`. Implemented on branch `feature/003-home-listado-hijos`, merged to `develop`.
- `specs/004-detalle-consulta-hijo/` — child detail page: lists a child's medical consultations, a form to register a new one (doctor, date, prescription photo, medications with dosing schedule, symptoms) with client-side OCR (`tesseract.js`) as an editable autofill aid (numbered prescriptions autofill one medication per line, added progressively with visible progress), and per-dose "tomada/no tomada" marking with no date/status restriction. New backend package `internal/consultation` (Consultation/Medication/Dose, all immutable except `Dose.taken`). Implemented on branch `feature/004-detalle-consulta-hijo`, PR: https://github.com/Ulisesgtz/medic-track/pull/4 (base `develop`), merged to `develop`.
- `specs/005-identidad-visual-front-end/` — visual identity and front-end redesign: PediTrack logo + PWA icons/manifest, design tokens (`frontend/src/index.css`, reference in `design-tokens.md` with the Tailwind recipes), all screens and both modals restyled, desktop children sidebar (`AppShell`, from 900px). Purely visual (FR-013): no route/API/data changes, except the consultation detail now returns medication `startTime` as `HH:MM`. **Every new screen must follow `specs/005-identidad-visual-front-end/design-tokens.md`** (see "Sistema visual" in `frontend/CLAUDE.md`). Implemented on branch `feature/005-identidad-visual-front-end`, PR: https://github.com/Ulisesgtz/medic-track/pull/5 (base `develop`), merged to `develop`.
- `specs/006-resumen-detalle-hijo/` — child detail summary matching the desktop mock: `GET /children/{childId}/overview?from=&to=` (today's doses in the parent's local day + the treatment still running, derived only from the dose schedule), `symptoms`/`medicationCount` on the consultations list, and `utcOffsetMinutes` on consultation creation so medication start times are read in the parent's time zone. Implemented on branch `feature/005b-alinear-mock-escritorio` (together with the desktop-mock alignment of the child detail), PR: https://github.com/Ulisesgtz/medic-track/pull/6 (base `develop`), merged to `develop`.
- `specs/007-homologar-pantallas-a-mocks/` — todas las pantallas hechas como los mocks entregados (tablero + `repo-pr/mockups/01…15`), con la lista de desviaciones y su motivo en su spec. **Los mocks web y los móvil son diseños separados y nunca se mezclan**: la app usa `useIsDesktop` (≥ 900 px = web) y renderiza uno u otro, sin clases responsivas `lg:` que combinen ambos. Nueva consulta es una página (`/children/:id/consultations/new`), "Agregar hijo" con el plan lleno abre el pop-up del plan de inmediato. Los registros (móvil 01 y web 11) tienen el campo Contraseña (solo validado, no se guarda) y el botón "Registrarme con Google" (aviso "pronto"): la autenticación real será con Clerk (ver `specs/008-autenticacion-cuenta/`). Implementado en `feature/007-homologar-pantallas-a-mocks`, PR: https://github.com/Ulisesgtz/medic-track/pull/7 (base `develop`), merged a `develop`.
- `specs/008-autenticacion-cuenta/` — autenticación real con **Clerk**, reemplazando el `account_id`-en-`localStorage` de specs/003/007 por una sesión de verdad: login (nuevo), el registro crea también el usuario en Clerk (contraseña real, "Registrarme con Google" real), `GET /accounts/{accountId}` y `POST /accounts/{accountId}/children` exigen que la sesión corresponda a esa cuenta, logout, recuperación de contraseña, y primer acceso para cuentas creadas antes de esta feature (se vinculan por correo verificado en `GET /accounts/me` o `POST /accounts`). Backend: `internal/authmw` (sesión y dueño), `internal/ownership`, `internal/server` (el router; **todo endpoint nuevo que nombre una cuenta/hijo/consulta se registra ahí con su `RequireOwner`**). Implementado en `feature/008-autenticacion-cuenta`, PR: https://github.com/Ulisesgtz/medic-track/pull/8 (base `develop`), merged a `develop`. Las E2E corren contra la instancia de desarrollo de Clerk (ver "E2E con Clerk" en `frontend/CLAUDE.md`); CI necesita los secretos `CLERK_SECRET_KEY` y `VITE_CLERK_PUBLISHABLE_KEY`.
- `specs/009-aviso-informativo-cuenta-nueva/` — aviso "Antes de empezar" en el home de quien acaba de crear su cuenta (la app es informativa y de seguimiento, no sustituye una consulta médica; el OCR se hace en el teléfono y la foto se guarda solo en su cuenta). Entregado en el PR #8, merged a `develop`.
- `specs/010-registro-aceptacion-aviso/` — auditoría del aviso: «Entendido» registra en el backend qué cuenta confirmó qué versión del texto y cuándo (`disclaimer_acceptances`, `POST /accounts/{id}/disclaimer-acceptance`, idempotente, solo dueño). Las respuestas de cuenta traen `disclaimerVersion`/`disclaimerAccepted`; el banner se muestra mientras sea `false` (cuentas nuevas, cuentas anteriores y cualquier cuenta cuando se sube `account.CurrentDisclaimerVersion` porque cambió el texto). Entregado en el PR #8, merged a `develop`.
- `specs/011-recordatorios-push/` — recordatorios de tomas por notificaciones push (PWA del teléfono y navegador de la PC): se activan por dispositivo, un aviso por toma a su hora aunque la app esté cerrada, detalle o texto genérico (el padre elige al activar la primera vez), acción "Tomada" desde el aviso. Backend: `internal/reminder` (dispositivos, reclamo de tomas vencidas —como máximo un aviso por toma—, envío Web Push cifrado, token HMAC de "Tomada", ticker de 30 s en el proceso del API; **el backend debe correr siempre** y necesita `VAPID_PUBLIC_KEY`/`VAPID_PRIVATE_KEY`/`VAPID_SUBJECT`/`REMINDER_ACTION_SECRET`, sin ellas los recordatorios quedan "no disponibles"). Frontend: primer service worker (`src/sw.ts`, `vite-plugin-pwa`) y `features/reminders/`. Probado de punta a punta en un iPhone real (PWA instalada, por el túnel de `DEPLOY.md`). Implementado en `feature/011-recordatorios-push`, PR: https://github.com/Ulisesgtz/medic-track/pull/9 (base `develop`), merged a `develop`.
- `specs/012-sintomas-notas-consulta/` — en "Nueva consulta" el padre marca los síntomas tocando chips por categoría (catálogo de 23 en la tabla `symptoms`, servido público en `GET /catalog/symptoms`; se amplía o se retira un síntoma con SQL, sin publicar la app) y el cuadro de texto pasa a ser "Notas previas a la consulta" (`consultations.symptoms` → `notes`, se conserva el texto de las consultas anteriores). Lo marcado se guarda en `consultation_symptoms` con la consulta, el hijo y la cuenta (llaves compuestas: la base no deja otro hijo ni otra cuenta), en la misma transacción que la consulta e inmutable. El listado resume "Fiebre, Tos, Vómito +2" y el detalle muestra las pastillas y las notas. Nunca un diagnóstico ni sugerencias (Principio I). Implementado en `feature/012-sintomas-notas-consulta`, PR: https://github.com/Ulisesgtz/medic-track/pull/10 (base `develop`), merged a `develop`. "Primera toma" (antes "Desde") es la hora de inicio de cada medicamento.
- `specs/013-tomas-sin-registrar/` — cuarto estado de cada toma (B2 del backlog): **sin registrar** = no marcada y ya llegó la siguiente toma de su medicamento (su hora + la frecuencia, también la última). Derivado por el servidor con su reloj y mandado como `status` (`pending`/`due`/`taken`/`unregistered`) en cada toma; sin columna nueva. Chip de borde punteado con "sin registrar", nunca rojo ni ámbar ni "no tomada" (Principio I); se puede marcar y desmarcar; las pantallas piden los datos cada 60 s. "Tomas de hoy" las cuenta aparte y "Marcar tomas" no las marca; el home no las cuenta; un recordatorio nunca se manda para una. Implementado en `feature/013-tomas-sin-registrar`, PR: https://github.com/Ulisesgtz/medic-track/pull/11 (base `develop`), merged a `develop`.
- `specs/014-progreso-tomas/` — barra de progreso por medicamento en el detalle de la consulta (B3): "3 / 9 tomas" (solo cuentan las marcadas) y "· 2 sin registrar" aparte. Derivado en el frontend de las tomas que ya llegan; sin backend ni API. Sin evaluar ni aconsejar (Principio I). Implementado en `feature/014-progreso-tomas`, PR: https://github.com/Ulisesgtz/medic-track/pull/12 (base `develop`), merged a `develop`.
- `specs/015-tomas-por-momento-del-dia/` — en cada medicamento del detalle de la consulta, las tomas del día se agrupan en Mañana (05:00–11:59), Tarde (12:00–18:59) y Noche (19:00–04:59) según su hora local (B1); los grupos vacíos no se muestran. Solo presentación en el frontend, sin API. Implementado en `feature/015-tomas-por-momento-del-dia`, PR: https://github.com/Ulisesgtz/medic-track/pull/13 (base `develop`), merged a `develop`.
- `specs/016-finalizar-tratamiento/` — botón "Finalizar tratamiento" por medicamento (B6), con confirmación neutral e irreversible. Guarda **cuándo** se terminó en `medications.ended_at` (migración `0013`) y **no toca ninguna toma**: las no marcadas cuya hora era posterior se derivan como `canceled` (quinto estado de la regla de la spec 013), no se pueden marcar y no se avisan. `POST /consultations/{id}/medications/{mid}/end` (solo el dueño, idempotente; 400 `nothing_to_end` sin tomas por delante). El tratamiento terminado deja de contar como activo, sale de "Tomas de hoy" y de los recordatorios, y la barra de progreso excluye las canceladas. Dice "Terminado el 30 sep · 6 de 9 tomas". Es la única excepción a la inmutabilidad de las consultas (spec 004, FR-014): solo cambia el fin. Implementado en `feature/016-finalizar-tratamiento`, PR: https://github.com/Ulisesgtz/medic-track/pull/14 (base `develop`), merged a `develop`.
- `specs/017-actualizar-datos-y-version/` — la app instalada se puede actualizar sola: **jalar hacia abajo** desde el tope vuelve a pedir los datos (solo diseño móvil, una vez en `AppShell`, sin recargar la página, así no se pierde lo capturado) y el aviso **«Hay una versión nueva · Actualizar»** (ambos diseños) cuando el build publicado (`/version.json`, escrito por `vite build`) difiere del que corre; recarga solo al tocarlo y pide confirmar si hay un formulario con datos (`shared/appVersion/unsavedWork`). Solo frontend, sin API. Implementado en `feature/017-actualizar-datos-y-version`, PR: https://github.com/Ulisesgtz/medic-track/pull/15 (base `develop`), merged a `develop`.
- `specs/018-errores-procesos-segundo-plano/` — lo que falla en el proceso de recordatorios (spec 011) ya no solo se imprime: queda en `error_logs` con `endpoint = job:reminders`, sin estado HTTP, archivo y línea y un mensaje fijo con conteos (nunca la dirección del dispositivo, claves ni tokens). Tres tipos: `tick` (no se pudieron leer las tomas), `prepare` y `deliver`; 404/410 y el cierre del servidor no cuentan. Agrupado: una fila por tipo cada 15 minutos con las veces calladas. Backend `internal/jobreport` (lo reutiliza cualquier proceso futuro). Sin migración, API ni pantallas. Implementado en `feature/018-errores-procesos-segundo-plano`, PR: https://github.com/Ulisesgtz/medic-track/pull/16 (base `develop`), merged a `develop`.
- `specs/019-calendario-tratamiento/` — en el detalle de la consulta, **un solo calendario mensual** (B4) antes de «Medicamentos»: cada día del rango de cada medicamento (de su primera a su última toma; con un tratamiento finalizado, hasta ese día) lleva su **número** en su **color** (seis tokens `--color-med-1…6`, sin rojo/verde/ámbar/cian; el número es el segundo indicador) y una leyenda con sus nombres; tocar un día lista debajo las tomas de ese día de todos los medicamentos, marcables con el mismo chip. Solo frontend: todo se deriva de las tomas y de `endedAt` del detalle, en hora local. No «recorre» ni cambia tomas (eso es B5). El orden de los medicamentos de una consulta es estable (`ORDER BY created_at, id`, `created_at = clock_timestamp()` al crear): el número y el color de cada uno dependen de su lugar. Implementado en `feature/019-calendario-tratamiento`, PR: https://github.com/Ulisesgtz/medic-track/pull/18 (base `develop`), merged a `develop`.
- `specs/020-recorrer-tratamiento/` — botón «Recorrer tratamiento» (B5, opción b) por medicamento, **solo por decisión del padre** (nunca automático ni sugerido): el diálogo propone tantas tomas como las tomas sin registrar aún no recorridas, el padre puede **confirmar o cambiar el número** (1–60; si lo cambia, nota de que lo ingresó manualmente), pregunta si su médico se lo indicó y avisa que queda registrado en su cuenta y que no se puede deshacer. `POST /consultations/{id}/medications/{mid}/extend` (solo el dueño) agrega las tomas al final con la frecuencia, registra cuenta/propuesto/confirmado en `medication_extensions` (migración `0014`, de solo agregar) y cubre las tomas sin registrar (`doses.covered_by_extension_id`) para no proponerlas dos veces (medicamento bloqueado en la transacción: dos dispositivos no duplican). El detalle trae `extendableDoses` y `extensions`; la tarjeta dice «Se recorrió el 30 sep · +2 tomas · número ingresado manualmente». Las tomas agregadas son tomas normales. **Segunda excepción a la inmutabilidad de las consultas** (spec 004): se agregan tomas. El calendario (spec 019) ahora marca solo los días con tomas y dibuja el **inicio y el fin** de cada medicamento como círculos rellenos de su color. Implementado en `feature/020-recorrer-tratamiento`, PR: https://github.com/Ulisesgtz/medic-track/pull/19 (base `develop`), merged a `develop`.
- `specs/022-rebranding-calendario/` — el calendario del tratamiento con el diseño nuevo de Claude Design (`referencia/Calendario PediTrack.dc.html`, medido y comparado lado a lado al ancho del mock): cada día del tratamiento es una pastilla celeste (`#ecfeff`) con **un punto por medicamento** que tenga tomas ese día —anillo del color, **relleno si todas las dosis del día se dieron**, vacío si no— y **lugar fijo** por medicamento; día elegido en tinta con aro cian; días fuera sin fondo; leyenda y lista del día con chips del diseño (verde «dada», ámbar «por marcar», punteado «sin registrar» y «próxima»); en la web, la tarjeta «Cómo leer el calendario». Colores nuevos `--color-med-1…6` (`#0e7490`, `#7c3aed`, `#db2777`, `#2563eb`, `#475569`, `#78350f`). Los círculos de inicio y fin de la spec 020 desaparecen de la vista (el diseño no los tiene; siguen en el nombre accesible). 12 desviaciones del mock listadas en la spec. Solo frontend. Implementado en `feature/022-rebranding-calendario`, PR: https://github.com/Ulisesgtz/medic-track/pull/22 (base `develop`), merged a `develop`.
- `specs/023-calendario-selector-de-dia/` — el calendario del detalle de la consulta es el **selector de día** de «Medicamentos» (opción b del backlog): se quita la lista «Tomas de hoy / Tomas del <día>» bajo el calendario y, al tocar un día, **cada tarjeta de medicamento** muestra las tomas de ese día (Mañana/Tarde/Noche, mismo chip), con el título «Tomas de hoy» / «Tomas del 3 de octubre» y «Este día no tiene tomas.» si no tiene. El día elegido vive en `ConsultationDetailPage` (`picked ?? initialDay(...)`, hoy si está dentro del tratamiento, si no el primer día) y baja al calendario (controlado) y a las tarjetas; el progreso y los botones siguen contando todo el medicamento. Las tomas canceladas de un tratamiento finalizado y las agregadas por un recorrido se alcanzan tocando su día. Se borran `DayDoses`, el aspecto `calendar` del chip y «próxima». Solo frontend. **No toca** el bloque «Tomas de hoy» del detalle del hijo (spec 006). Implementado en `feature/023-calendario-selector-de-dia`, PR: https://github.com/Ulisesgtz/medic-track/pull/23 (base `develop`), merged a `develop`.
- `specs/024-consulta-solo-registro/` — al crear una consulta, el checkbox **«Consulta anterior: guardar solo como registro»** la guarda sin horarios ni alertas, solo informativa: doctor, fecha, foto, síntomas, notas y medicamentos (nombre, frecuencia y duración) pero **sin «Primera toma» y sin tomas**; no cuenta como tratamiento activo, no entra en «Tomas de hoy» ni manda recordatorios (todo eso se deriva de las tomas, y sin hora de inicio no se generan). Columna `consultations.record_only` (migración `0016`, por omisión `false`; se fija al crear y no se cambia: consultas inmutables), `recordOnly` en la petición y en el listado y el detalle (compatible hacia atrás; el servidor descarta la hora de inicio si llega). En el listado y el detalle lleva la etiqueta neutra «Solo registro» (`RecordOnlyBadge`); el detalle no muestra calendario, tomas, progreso, botones ni «Tratamiento activo». La fecha sigue sin poder ser futura. Implementado en la misma rama que la 023 (`feature/023-calendario-selector-de-dia`), PR #23, merged a `develop`.
- `specs/027` (sin carpeta: cambio chico de diseño, documentado en la spec 022) — **marca de «hoy» en el calendario**: hoy lleva un aro fino de tinta (`ring-[1.5px] ring-inset ring-ink`) mientras el padre eligió otro día (el elegido ya es la celda oscura); además se cerraron dos decisiones de la auditoría de Design Claude: `--color-med-1` = `--color-action` (`#0e7490`) **se deja igual** y la desviación 12 de la spec 022 (**«sin registrar» punteado, nunca ámbar**) queda cerrada. Implementado en `feature/027-marca-de-hoy`, PR: https://github.com/Ulisesgtz/medic-track/pull/27 (base `develop`), merged a `develop`.
- `specs/028` (sin carpeta: refactor sin cambio visual) — **los colores sueltos pasaron a `@theme`**: las clases ya no escriben `text-[#67e8f9]` sino tokens (`bg-bright-soft`, `border-hint-edge`, `text-body`, `text-ink-muted`, `border-ink-edge`, `text-on-pending-muted`, `bg-mint`, `text-calendar-muted`/`-text`/`-name`; los que ya existían —`hint`, `hint-border`, `bright`, `confirmed-strong`, `on-pending`, `pending-strong`— se reutilizan). 100 reemplazos en 25 archivos; el CSS compilado resuelve a las **mismas 436 declaraciones** que antes. `noColorLiterals.test.ts` falla si alguien vuelve a escribir un color literal en una clase (el SVG del logo de Google es marca y queda fuera). Los tonos pizarra del calendario llevan el valor **exacto** del diseño (los `slate-*` de Tailwind v4 son oklch y salen 2–3 niveles distintos). Implementado en `feature/028-colores-a-theme`, PR a `develop`.

- `specs/029` (sin carpeta: cambio chico) — **plan de pago para quien prueba**: el enum `account_plan` ya tenía `free`/`paid`; ahora `account.ChildLimit(plan)` da 1 hijo al plan gratuito y **10** al de pago (`AddChildIfUnderLimit` lee el plan bajo el bloqueo de la fila). Sin migración, API ni pantallas nuevas: el frontend ya mostraba «Plan completo» y no pedía el aviso de límite a `paid`. Se da a mano con SQL (`UPDATE accounts SET plan = 'paid' WHERE …`, ver `backend/CLAUDE.md`); no hay endpoint ni cobro. Implementado en `feature/029-plan-premium`, PR a `develop`.
- `specs/030-reglas-plan-gratis/` — **el plan gratuito guarda una consulta con tratamiento activo a la vez y no puede guardar «solo registro»**; lo ya registrado siempre se ve (decisión de producto del 2026-10-05, primer paso del «Orden sugerido» de `BACKLOG.md`, «Qué incluye el plan de pago»). `POST /children/{id}/consultations` de una cuenta gratuita con otro tratamiento activo en **la cuenta** (medicamento sin finalizar con una toma por delante, la misma noción de «activo» del resumen del hijo) responde 422 `freemium_consultation_limit_exceeded` con `reason` `active_treatment`, y con `recordOnly: true` con `record_only`; la revisión es atómica (bloquea la fila de la cuenta en la transacción de `Repository.Create`). Una cuenta de pago no tiene ninguno de los dos límites. En la app, «Nueva consulta» (detalle del hijo en ambos diseños y detalle de la consulta en la web) abre el aviso del plan **antes** de mostrar un formulario que se rechazaría (`NewConsultationEntry`), el formulario muestra el mismo aviso si el servidor rechaza al guardar sin perder lo escrito, y la casilla «solo registro» se ve deshabilitada en el plan gratuito. Sin migración ni pantallas nuevas. Los seeds de las E2E son de pago por omisión (`setAccountPlan`, helper con `pg`). Implementado en `feature/030-reglas-plan-gratis`, PR a `develop`.
- `specs/031-historial-busqueda-filtros/` — **Historial con búsqueda y filtros, solo del plan de pago** (segundo paso del «Orden sugerido» de `BACKLOG.md`). Una pantalla por hijo (`/children/:childId/historial`, dos diseños, sin mock) con texto (doctor, notas o nombre de un medicamento, sin distinguir mayúsculas ni acentos, por parte de la palabra) y filtros por fechas, doctor, medicamento, síntomas (todos los marcados) y tipo (todas / con tratamiento / solo registro), todos a la vez; los resultados son las mismas tarjetas y el mismo detalle de la lista. Backend: `POST /children/{id}/consultations/search` (**el criterio va en el cuerpo, no en la dirección**: el texto puede ser un dato de salud y el API y los proveedores registran las direcciones) y `GET /children/{id}/history-options` (doctores y medicamentos ya registrados); el servidor decide el plan y rechaza al gratuito con 422 `freemium_consultation_limit_exceeded` `reason: "history_search"` **sin resultados**. Sin migración ni dependencias. El plan gratuito **sigue viendo toda su lista**; en ella «Buscar en el historial» lleva la marca «Plan completo» y abre el aviso del plan (`HistoryEntry`). ## Conventions (full detail in the constitution)

- **Code language**: all code, identifiers, DB schema/columns in English. Docs (specs, plans, constitution, commit prose) in Spanish.
- **Git**: `feature/NNN-slug` / `bugfix/NNN-slug` branches off `develop`, PR back to `develop`. `master` only updated on deploy.
- **Testing**: >90% unit coverage (Go + React) is required per Principio VI; Playwright E2E required for critical flows. Run before every push:
  - Backend: `cd backend && go test ./... -cover` (needs `DATABASE_URL` env pointing at a local Postgres)
  - Frontend unit: `cd frontend && npx vitest run --coverage`
  - Frontend E2E: `cd frontend && npx playwright test` (needs backend + frontend dev servers running)
- **CI**: `.github/workflows/ci.yml` runs the backend coverage gate, frontend coverage gate, and Playwright E2E gate on every PR/push to `develop`/`master`. `cmd/api` (Go entrypoint wiring) is excluded from the backend coverage gate — standing open question, not yet resolved with the user.
- **Web mocks are for web, phone mocks for phone — never mix them.** Each screen has a phone design and a web design (mocks 01–05 vs 11–15 and the board). Render exactly one per viewport with `useIsDesktop` (`frontend/src/shared/ui/`), and test both (E2E runs every flow at 390 px and 1280 px).
- **When the user gives a mock, build exactly that mock** (structure, sections, order, texts, colors, sizes) — not an interpretation, and not a substitute made from whatever data already exists. Before saying it's done: (1) measure the mock (its scale, frame width, sizes and positions — e.g. sample the image with PIL) and render the app at the mock's own width; (2) put mock and app side by side and check section by section, not just pixels of one element; (3) if the mock shows data the API doesn't have, build the data (endpoint, spec) instead of swapping in different content; (4) list every remaining deviation with its reason (e.g. a color that would break the 4.5:1 rule) and let the user decide. Ask only when genuinely blocked. The mock wins over `design-tokens.md` where they differ, except accessibility minimums, which must be flagged rather than silently broken.
- **When you add a new module/feature**: update this file and the relevant `backend/CLAUDE.md`/`frontend/CLAUDE.md` map — they don't update themselves.
- **Every new backend endpoint MUST write its responses through `*httpx.Responder`** (see backend/CLAUDE.md's "Automatic error logging") so it's automatically captured in `error_logs` — not optional, and there's no other supported way to write a JSON response in this backend.
- **When a conversation decides something is future work** (explicitly deferred, not building it now): add it to `BACKLOG.md` instead of only noting it in a spec's Supuestos or in memory — specs get buried once done, and memory isn't visible in the repo to anyone else.
